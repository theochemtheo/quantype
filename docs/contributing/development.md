# Development

## Setup and commands

From a checkout, [install uv](https://docs.astral.sh/uv/getting-started/installation/)
and run the following at the repository root. `just` and the type checkers
come with the development dependencies, so you don't need to install `just`
globally.

```bash
git clone https://github.com/theochemtheo/quantype.git
cd quantype
uv sync --all-extras
uv run just generate
uv run just check-generated
uv run just test
uv run just typecheck
uv run just stubcheck
uv run just lint
uv build
```

For a lighter environment, install only the `test` dependency group and at
most one backend, as CI's tier jobs do:
`uv sync --no-default-groups --group test --extra jax`, then
`uv run --no-sync pytest tests/runtime README.md docs -rs` (optional-backend tests
and explicitly backend-dependent examples skip when unavailable). The `dev`
group includes `test` and `docs`, so a plain `uv sync` includes the site builder.
The `just test`, `just typecheck`, `just stubcheck`, and `just lint` recipes
request all extras. `just typecheck` runs the type checkers and the negative
conformance suite; `just stubcheck` runs mypy's stubtest, which compares every
stub with the runtime and takes about a minute, so run it when stubs or the
generator change. CI runs both.
To install the repository's commit hooks, run `uv run just setup`.
The Ruff formatting hook also formats Python fences in Markdown. Ruff linting
remains scoped to Python files.

`just lint` runs [zizmor](https://github.com/zizmorcore/zizmor) offline against the
GitHub Actions workflows; the pre-commit hook checks workflow changes too.

## Package layout

The top-level `quantype` import provides quantities and `u`; `quantype.units`
holds the unit namespaces. `quantype.numpy` has NumPy's names with unit rules,
`quantype.constants` the physical constants, `quantype.products` the classes
for unnamed products of two kinds, `quantype.testing` test assertions, `quantype.systems` the unit systems, and
`quantype.codata` the CODATA edition. Use `quantype.serialization`
for JSON/NPZ boundaries, `quantype.ujax` or `quantype.utorch` for optional
autodiff, and `quantype.catalogue` with `quantype.codegen` for application
catalogues. `quantype.core` and `quantype.kinds` expose base types and
structural markers for advanced annotations. Implementations live in
`quantype._internal`; the public modules only re-export them.

## Coverage

`uv run just coverage` syncs every extra and runs `scripts/coverage.sh`: one
pytest run with every backend present, including subprocesses the tests start,
writing `htmlcov/`, `coverage/quantype.lcov`, and `coverage/summary.md`, and
failing below 98% line-and-branch coverage (`COVERAGE_MIN` overrides it). CI
posts the summary to the job and to pull requests, and on `main` writes the
README badge's figure to the `badges` branch.

CI measures coverage on Python 3.14, where coverage traces branches through
`sys.monitoring`; on 3.12 it falls back to `sys.settrace`, and the suite takes
more than twice as long. `UV_PYTHON=3.14 uv run just coverage` matches CI.

## Dependency tiers

CI runs the suite in the full environment and in deliberately incomplete ones:
the `test` group alone, with JAX, and with Torch, plus the oldest supported
NumPy and Pydantic. Each job sets `QUANTYPE_TEST_TIER`, and a canary in
`tests/runtime/test_optional_backends.py` fails when the installed backends
differ from the tier's, so a tier cannot pass by quietly skipping. Import guards
that only run when a backend is missing are tested in-process
(`test_install_hints.py`), so they count toward coverage.

## Conformance

The conformance suite checks runtime behavior, positive and negative typing
examples across mypy, Pyright, Pyrefly, and ty, and runtime/stub agreement.
`tests/runtime` also runs the positive typing examples, which keeps the stubs
and the runtime in step. CI tests core-only, JAX-only, Torch-only,
and minimum-core-dependency environments.

The unit-system parameter's default needs PEP 696. The stubs use
`typing_extensions.TypeVar` for it, since PEP 695 syntax cannot express defaults
before Python 3.13. The development dependencies pin the oldest checker versions
tested with it.

## Generated files

`uv run just generate` regenerates, and `uv run just check-generated` checks:

- `src/quantype/_internal/_codata.py`, the vendored CODATA table, from the NIST
  tables SciPy bundles (`scripts/generate_codata.py`; SciPy is a development
  dependency only);
- the built-in API (`_generated.py`/`.pyi`, `kinds.py`, `units.py`/`.pyi`,
  `numpy.py`/`.pyi`, `ujax.pyi`, `utorch.pyi`), rendered from the built-in
  catalogue by `quantype.codegen` (`scripts/generate.py`);
- `docs/reference/catalogue.md`, the kinds and units reference (`scripts/generate_docs.py`).

`docs/reference/units.md` also contains a numerical-range table generated by
`quantype._internal._systems.range_table`; `tests/runtime/test_systems.py`
fails when it is stale.

## Documentation workflow

The [documentation homepage](../index.md) routes user pages by tutorial, task,
reference, and explanation. Handwritten reference documents contracts that
runtime introspection cannot recover from generated stubs; the catalogue
reference comes from its renderer.

| Command | Contract |
| --- | --- |
| `uv run just docs-serve` | Live working-tree preview at `http://127.0.0.1:8765/quantype/`; opens a browser |
| `uv run just docs-test` | Sybil examples in README and published user pages, with visible skip reasons |
| `uv run just docs-build` | Clean, strict production build; never executes examples |
| `uv run just docs-check` | Examples, generated catalogue freshness, strict build, local targets, and agent exports |
| `uv run just docs-preview` | Build and serve actual production output at `http://127.0.0.1:8766/quantype/` |

The production preview snapshots the built artifact, so editorial rebuilds do
not change it. Stop and restart `docs-preview` to review a newer production build.

Site commands use the `docs` dependency group. Sybil belongs to `test`, so
`uv run --no-default-groups --group test pytest README.md docs -rs` checks
examples without requiring Zensical or installing optional backends.
For final all-example proof, install every backend with
`uv sync --locked --all-extras`, then run
`uv run --all-extras just docs-check`. Missing-backend skips make a partial run
useful but not full proof. Full suite and coverage commands include Markdown;
xdist uses file-based scheduling so a tutorial stays on one worker.

### Site presentation

`docs/stylesheets/glacier.css` owns the Ledger layout, Glacier palettes, and
self-hosted Atkinson Hyperlegible/Iosevka font declarations. Keep the selected
font binaries and their [Atkinson](../fonts/atkinson/OFL.txt) and
[Iosevka](../fonts/iosevka/LICENSE.txt) licenses together under `docs/fonts/`.
`zensical.toml` disables automatic Google Fonts loading and starts in dark mode;
the palette control also supports light mode.
Code blocks align with surrounding content at every screen size, retaining
internal padding and the right-edge accent. Sidebar groups are collapsible;
the current page's ancestry starts open.

### Changelog source

Edit the root `CHANGELOG.md`; `docs/changelog.md` includes it at build time using
Zensical's native `include-markdown` support. Do not maintain a second copy of
release notes. The preview watches the root file for updates. Use absolute
repository URLs for source links so they work both on GitHub and in the site.

### Author examples

Use plain, top-level `python` fences for scripts and `>>>` doctest transcripts.
Tutorials execute in order with shared page state. All other user-page and
README fences are independent, including their visible imports; prompts within
one transcript retain state. Filesystem examples run in a pytest-managed
temporary directory. Installation shell blocks and historical examples are not
Python tests.

Put `<!-- requires: jax -->` or `<!-- requires: torch -->` immediately before
each backend-dependent fence (comma-separated for both). Only unavailable
declared backends skip. Use Sybil's `<!-- skip: next "Specific reason" -->`
for genuinely illustrative pseudocode, never to hide an ordinary failure.
Assert expected errors and numerical results. Do not use annotated/nested
Python fences, invisible setup, or the old `python notest` convention.
Inferred types and rejected expressions additionally need the existing
four-checker [conformance](#conformance) fixtures.

Put installation requirements in the tutorial, not repeated core-dependency
notes on every page. Call out genuinely optional tools/backends where needed.
Use noncollapsible admonitions for important cautions and decisions, and keep
Python fences outside them. Link a term's first important use to the
[glossary](../explanation/glossary.md) with a short link title for its hover
definition. Hover text supplements visible explanations; it never carries a
restriction on its own.

### Review and agent access

The site documents development on `main`, not the latest PyPI release. Every
build labels its package version and full source revision; local builds also
identify working-tree content. `llms.txt` is curated from the same published
pages, with generated Markdown and a Copy as Markdown action; do not author a
parallel agent manual. Production excludes proposals, design notes, superseded
decisions, and templates. Accepted decisions and contributor guidance have a
separate navigation section.

Before broad reorganization, build one real page in each reader mode, run its
examples, inspect it in a browser, and obtain structural review. Before a PR,
run full-backend examples, relevant typing fixtures, generation checks, strict
build, local link/export checks, and scoped formatting/workflow checks. Review
both live editorial output and the actual production build under `/quantype/`,
including search, deep links, assets, narrow/light/dark layouts, code copying,
Markdown access, exclusions, and build identity. Leave both servers available
for feedback and obtain complete-site approval before opening a PR.

### Publication remains disabled

PRs and code-only changes run required documentation checks. The Pages workflow
checks a `main` revision before uploading its SHA-named production artifact.
Only deployment has Pages/OIDC write permissions. Upload and deployment require
the repository variable `QUANTYPE_PAGES_ENABLED` to equal `true`; leave it unset
until publication is explicitly authorized. Enabling repository Pages or
changing that variable is a separate remote action, not part of local review.
